## 二、发现的问题

### 问题 1：Type Matrix 过严导致 28% 行丢失关系 🔴

**现象**：70/250 行在 `disagreement_flags_json` 中出现 `LLM_RELATION_DROPPED_INVALID_SCHEMA`。LLM 正确输出了关系，但被后处理规则丢弃。

**三类被拒场景**：

| 场景 | LLM 输出 | 被拒原因 | 影响行数（估计） |
|------|----------|----------|-----------------|
| EQUIPMENT USES EQUIPMENT | 猎人无人机 USES GPS制导毒蛇 | USES 只允许 EQUIPMENT→MODULE | ~30 |
| MODULE HAS_METRIC 非METRIC | 四联装发射架 HAS_METRIC 破片战斗部 | HAS_METRIC 只允许 tail=METRIC | ~20 |
| EQUIPMENT× HAS_METRIC 非METRIC | AN/SPS-48E HAS_METRIC 探测能力 | 同上 | ~15 |
| 其他 | 引用已删除实体等 | overlap 解析副作用 | ~5 |

**典型案例**：

- `domain-candidate-0140`（猎人无人机）：LLM 输出 `无人机 USES GPS制导型毒蛇武器系统`，两者均为 EQUIPMENT → 被丢弃。原文明确描述了武器系统装备到无人机上，关系语义正确。
- `domain-candidate-0141`（SPS-48E）：LLM 输出多条 `AN/SPS-48E HAS_METRIC 探测跟踪能力`，tail 为 TECH_SCHEME → 全部被丢弃。
- `domain-candidate-0001`（萨姆-14）：`四联装发射架 HAS_METRIC 1公斤破片战斗部`，tail 被分类为 MODULE → 被丢弃。

**修复方案**（不重跑 GPU，只改后处理）：

```python
# 当前规则
USES:        EQUIPMENT → MODULE | TECH_SCHEME
HAS_METRIC:  EQUIPMENT → METRIC
PART_OF:     MODULE → EQUIPMENT

# 建议放宽为
USES:        EQUIPMENT → MODULE | TECH_SCHEME | EQUIPMENT
HAS_METRIC:  EQUIPMENT | MODULE → METRIC | TECH_SCHEME
PART_OF:     MODULE | EQUIPMENT → EQUIPMENT | MODULE
```

**预期效果**：relation 覆盖率从 66% → ~85%，丢弃率从 28% → <5%。

### 问题 2：METRIC/MODULE 分类退化 🟡

**现象**：v4 (p2-llm-label-v4) 中正确分类为 MODULE 的实体，在 v5 中被错误分类为 METRIC。

**具体案例**：

| 实体 | v4 分类 | v5 分类 | 正确分类 |
|------|---------|---------|----------|
| 90g B炸药 | MODULE ✅ | METRIC ❌ | MODULE |
| 210千克半穿甲战斗部 | — | METRIC ❌ | MODULE |
| 1公斤破片战斗部 | MODULE ✅ | MODULE ✅ | MODULE |

**根因**：v5 prompt 中 METRIC 的定义可能过于宽泛，LLM 将"含数值的实体"一概标为 METRIC，而忽略了实体的功能性（炸药/战斗部是组件而非度量值）。

**修复建议**：在 prompt 中增加 2 条规则：
- "含重量/尺寸数值但本身是武器组件的实体（如'90g B炸药''210千克半穿甲战斗部'）应标为 MODULE，而非 METRIC"
- "METRIC 仅用于纯度量值，如'射程300公里''重量10公斤''口径122毫米'，不用于含度量值的产品名称"

### 问题 3：实体类型边界错误 🟡

| review_id | 实体 | v5 分类 | 正确分类 | 说明 |
|-----------|------|---------|----------|------|
| domain-candidate-0002 | 岸基 | EQUIPMENT | 不标注或 DEPLOYMENT_MODE | "岸基"是部署方式，不是装备 |
| domain-candidate-0002 | 意大利、法国等10国海军 | EQUIPMENT | 不标注或 ORGANIZATION | 军队组织，不是装备 |
| domain-candidate-0240 | 120毫米火炮 | EQUIPMENT | MODULE | 在坦克语境下是组件，非独立装备 |
| domain-candidate-0060 | 信道状态信息 | METRIC | TECH_SCHEME | 是信息/参数概念，非度量值 |
| domain-candidate-0060 | 干扰信道参数矩阵 | METRIC | TECH_SCHEME | 同上 |

**修复建议**：
- Prompt 中增加：ORGANIZATION、LOCATION、DEPLOYMENT_MODE 等不在 schema 中的概念应跳过，不要强行映射到 EQUIPMENT
- 增加 MODULE vs EQUIPMENT 的语境判断规则：同一实体在"独立武器系统"语境下为 EQUIPMENT，在"某平台的组成部分"语境下为 MODULE

### 问题 4：PART_OF 方向错误 🟡

**现象**：当 head 和 tail 都是 EQUIPMENT 时，LLM 有时搞反 PART_OF 方向。

| review_id | LLM 输出 | 正确关系 |
|-----------|----------|----------|
| domain-candidate-0240 | 公羊主战坦克 PART_OF 120毫米火炮 | **120毫米火炮 PART_OF 公羊主战坦克** |
| domain-candidate-0001 | 舰载型SA-N-8 PART_OF 四联装发射架 | **四联装发射架 PART_OF 舰载型SA-N-8** |

**根因**：PART_OF 的语义是"head 是 tail 的一部分"。当两个实体都是"东西"（同为 EQUIPMENT 或同为 MODULE）且大小关系不明显时，LLM 缺乏判断哪个是整体、哪个是组件的常识推理。

**修复建议**：
- 在 prompt 的 PART_OF 示例中增加方向性说明："PART_OF 的 head 必须是较小的组件，tail 必须是较大的整体。例如'炮管 PART_OF 坦克'✓，'坦克 PART_OF 炮管'✗"
- 考虑在 type matrix 中增加方向合理性检查（虽然实现上有难度）

### 问题 5：永久 Parse Failure（2.8%）⚠️

7 条全部是同一模式：`entity N occurrence 1 not found for 'XXX'` — LLM 生成了原文中不存在的实体名称（改写/缩写/翻译导致名称不匹配），span 定位器无法在原文中找到。

| review_id | 来源 | 预期实体（推测） |
|-----------|------|-----------------|
| domain-candidate-0008 | patent | 含中文特殊字符的电子元件名 |
| domain-candidate-0049 | patent | 加密装置名称 |
| domain-candidate-0109 | cmnee | 雷达型号 |
| domain-candidate-0133 | cmnee | 长武器系统名 |
| domain-candidate-0194 | cmnee | 飞行器型号 |
| domain-candidate-0213 | cmnee | 直升机名称（AH-64相关） |
| domain-candidate-0238 | cmnee | 空地导弹 |

**根因**：LLM 有时会"规范化"实体名称（加/减修饰语、翻译、缩写展开），导致 span 不可定位。这是 LLM NER 的已知局限性。

**修复建议**：
- 重试机制已生效（都试了 2 次），无需改动
- 在人工标注流程中对这 7 条标记为"LLM 失败，需从零标注"
- 长期方案：考虑 fuzzy span matching（允许编辑距离 ≤2 的近似匹配）
